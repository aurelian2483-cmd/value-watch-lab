## Can these methods establish exact bytes before the cutoff?

The required claim is existence of the exact canonical forecast bytes before the registered deadline, five minutes before the scheduled start. A provider receipt, forecast generation time, ledger commit time or local observation alone cannot prove this. Preserve the original forecast bytes. Changing an attestation flag inside the forecast after receiving the token would change the bytes under proof. The witness lives in a separate ledger record.

## Source eligibility and end-to-end acceptance

The fixture path uses three separately pinned Ed25519 identities with explicit permission, retention limits, source roles, owners and upstream lineage. It retains exact signed acquisition bytes before freezing and rechecks the link to the verified freeze event on read. Freshness is tested at acquisition and at the original transactional freeze limits. A previously frozen, unauthorised feed cannot become authorised retrospectively.

The forecast is frozen transactionally first, which establishes the precise bytes submitted for witnessing. Eligibility for even fixture evaluation waits for a valid witness and two reconciled result receipts. Signed result receipts must agree on scheduled race identity, course, full unique runner field, winner and revision. They must postdate the event and fall within the observed time and retention limits. A signed amendment must link to both prior receipt hashes and have a later publication time. The adapter rejects fallback to an older forecast when a newer revision exists. Evaluation uses the unchanged registered A/B metrics and reproduces after restart and backup restore. Fixture scores are never written into the registered archive or presented as validation.

No external results or historical market dataset was acquired. The earlier [source verification](../source-verification.md) remains applicable. The BHA official full result flows to Weatherbys, stewards and media through the race-day distribution system, so distinct publishers can share the same source. RMG describes paid/licensed data for its listed courses and a PA delivery arrangement. Betfair supplies historical market and settlement data with registration and separate product terms. Settlement and price snapshots are historic market evidence with their own provenance, completeness and publication-delay questions. Live eligibility still requires permission for storage and independent review, full declared field coverage and runner identifiers, a defensible scheduled-off and publication-time chain, correction history, and independently reviewed source lineage distinct from simple republication. [BHA official results distribution](https://www.britishhorseracing.com/faqs/how-is-the-official-full-race-result-distributed/) · [RMG race-day data](https://racecoursemediagroup.com/structure-area/race-day-data/) · [Betfair historical data](https://support.developer.betfair.com/hc/en-us/articles/360002407732-What-data-is-provided-by-the-Historical-Data-service)

## Transaction and recovery evidence

The original eight intake and seven scheduler hard-exit cases were reproduced. Cross-process uniqueness, missed schedules, per-record cutoff and isolation continue to run through the original 27 tests. The qualification path independently checks that the forecast, race index and audit event agree. It closes two observed integrity gaps in the earlier disposable snapshot inspection. Changing a projected capture timestamp or appending trailing bytes to a JSON object with the same canonical value could pass that snapshot. Both changes now fail qualification and backup integrity checks.

The backup adapter uses the SQLite online backup API, verifies exact-byte hashes, forecasts and audit projections, checks SQLite integrity and foreign keys, and publishes a complete snapshot through an exclusive same-directory link and sync. Restore verifies the pinned manifest and never replaces a target DB. Independent tests cover concurrent writes, corrupted database bytes, a truncated backup, process exit during copy and before publication, simulated disk failure, recovery after directory sync failure and replay of signed evidence after restore. Separate process exits test witness recording on both sides of the commit boundary. The tests establish behaviour on the disposable local POSIX filesystem. Real power loss, network volumes and multi-host operation remain unqualified. [SQLite online backup API](https://www.sqlite.org/backup.html)
