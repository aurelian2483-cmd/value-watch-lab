# Unified Research Control Centre — Phase 2 foundation

Separate stacked branch based on Phase 1 accepted head ead68f5d893cbe6428e374e7a9216a1633077dfc. No original project changes. The initial integration supports local, explicitly approved batches of six summary files, one atomic accepted state, receipt age, and an opt-in loopback viewer. It does not run producers, poll external sources, collect datasets, start on boot or authorize research.

## Controlled intake
Create two separate existing directories for the inbox and state, owned by the operator and not writable by untrusted processes. Copy only the six aggregate summary files named in the inherited source-pins.json into the inbox. An operator must review the exact source and contents before approving. Provide approval.json with kind APPROVED_SUMMARY_BATCH, schemaVersion 1, sequence (starts at 1 and increases by exactly one), approvedAt (UTC ISO time with milliseconds), and sources in pin order with id, head, reportRevision, run, artifact and summarySha256. Identity fields must match the inherited pins. The expected SHA-256 of the exact approval bytes must come from a separately trusted review; merely hashing an untrusted manifest is not authentication.

Run:
- node research/unified-live/sync.mjs sync <inbox> <state-dir> <trusted-approval-sha256>
- node research/unified-live/sync.mjs status <state-dir>
- node research/unified-live/viewer.mjs <state-dir> 8766

Open http://127.0.0.1:8766 on the same computer. The viewer reloads every 15 seconds; it reads accepted state, not the inbox. Stop it using Ctrl+C. No server is installed or started automatically. Any local process can read this loopback service, so do not expose it or use it with sensitive raw data. Only GET/HEAD are supported. No remote access or CORS.

Each batch is staged, validated by the inherited adapters, independently checked against approved byte hashes, and committed to current.json with a writer lock and atomic replacement. Replays do not refresh receipt age. Unchanged individual reports retain their first-received timestamp across batches. Missing, corrupted, out-of-order, unapproved or unsafe files do not replace accepted state. The status distinguishes no accepted batch, recently received, stale and clock uncertain. Measurement freshness always remains UNKNOWN; receipt age is not producer health. State corruption fails closed. A leftover writer lock after interruption requires manual verification that no writer is running before removal. Atomic replacement is not a power-loss durability guarantee; backup and restoration acceptance are subsequent milestones.

## Scope and provenance
Initial adapters are deliberately bound to the Phase 1 revision set; changed report bytes are local operator-approved candidates, not proof that an immutable GitHub artifact has changed or that a producer supplied them. The source labels remain declared, not authenticated by the viewer. CI independently downloads the five exact verified historical archives and the pinned Git catalogue and exercises the real aggregate contracts. Synthetic fixtures test sequencing and changed bytes; they are not research results. New source revisions and automatic producer feeds require reviewed promotion, source-specific provenance and explicit authorization in subsequent development. No automatic approval is provided outside isolated CI. The local state directory is a trusted operator boundary; self-hashes do not defeat deliberate re-signing by an attacker with write access.

## Checkpoint and isolated recovery

Create a separate operator-owned backup directory and a new empty recovery directory. Run node research/unified-live/sync.mjs checkpoint <state-dir> <backup-dir> and retain the emitted sequence and checkpointSha256 separately in a trusted record. Run node research/unified-live/sync.mjs recover <backup-dir> <empty-state-dir> <trusted-checkpoint-sha256> <sequence>. The operation never overwrites active state or existing checkpoints, rejects mismatched hashes and preserves original timestamps and approval sequence. Inspect the recovered state using status before manually selecting it for a new viewer. There is no automatic failover or active rollback; an older isolated checkpoint is historical and must not be presented as newer evidence. Recovery is not proof of physical disk durability or independent provenance. Do not use operator directories writable by untrusted processes. The earlier baseline 4fd2f73 passed 14 tests, thirteen browser scenarios including timed refresh, and full regression (runs 45505643944 and 45505644034). Checkpoint/recovery tests and actual CI recovery are pending on the new revision.

## Latest rejected update

The viewer presents a bounded receipt for the latest rejected sync attempt after the writer lock is acquired. It records only an allowlisted stage, observed time and previous accepted sequence/state fingerprint; no raw data, paths, error strings or automatic repair action. A subsequently accepted generation marks an older rejection historical rather than erasing it. Missing receipt means NO_REJECTION_RECORDED, not proof that no failures occurred. Corrupt or inconsistent receipt evidence is explicit; the accepted snapshot remains unchanged. Pre-lock/configuration failures and interrupted processes may not have a receipt; failure to write a receipt is reported to the operator. This is not a complete incident ledger, authenticated supervisor feed, or automatic recovery. Checkpoint recovery preserves accepted state only, not the separate incident receipt. Baseline 13d57c7 passed 18 tests, 13 browser scenarios and actual isolated recovery (45506123866), plus full regression (45506123895). New incident tests pending CI.

## Optional signed producer intake

The local adapter producer-intake.mjs accepts six distinct Ed25519 public keys in an operator-approved trust registry, plus a six-signature envelope file. It requires both registry and approval SHA-256 fingerprints from a separate trusted review. It binds signatures to producer ID, fixed revision, workflow/artifact identity, exact summary digest, approval digest, batch sequence and a maximum one-hour validity window. It stages verified bytes and reuses the existing atomic synchronisation engine. Run node research/unified-live/producer-intake.mjs <inbox> <state-dir> <trust-file> <trusted-trust-sha256> <trusted-approval-sha256>. Retain the emitted receipt separately. The registry contains public keys only, never private keys. No production keys are provisioned; no automatic producer signing, service, network connection or approval is configured. Manual intake remains available for unsigned states. Once a state accepts signed evidence, unsigned updates and unreviewed trust-registry changes are rejected. Public signature evidence is stored atomically with accepted state; source labels remain declared rather than independently authenticated GitHub provenance. Authentication verifies possession of an approved key, not scientific validity or GitHub provenance. Preflight failures before the core synchronisation lock do not create a rejected-update receipt. CI uses ephemeral test-only keys on previously verified historical aggregates. Baseline 985112a passed 22 tests, 13 browser scenarios and full regression (45506616337 and 45506616382); new signed intake tests pending.

## External trust and exact state review

Optional anchored status and viewer modes accept a separately retained trust registry SHA-256. A second optional SHA-256 pins the exact accepted state fingerprint. The trust anchor must originate from the operator's trusted record, not from the state being reviewed. The state anchor requires the trust anchor. Run node research/unified-live/sync.mjs status <state-dir> <trusted-trust-sha256> [trusted-state-sha256], or node research/unified-live/viewer.mjs <state-dir> 8766 <trusted-trust-sha256> [trusted-state-sha256]. Each status request revalidates the stored signatures at the original acceptance time and compares the supplied anchors. Missing signed state or mismatched anchors cause failure rather than a downgrade. Exact-state mode intentionally refuses newer generations until the operator supplies their independently retained state fingerprint and restarts the viewer; trust-only mode checks signing identities without pinning the complete state or preventing rollback. Without supplied anchors, the default remains explicitly unanchored. This is local operator review, not a live external trust service or scientific validation. Production trust anchor provisioning and key rotation remain outstanding. CI uses isolated ephemeral test keys and verified historical inputs only. New tests pending.

## Bounded automatic local collection

Baseline ee66b62 passed 34 tests, 13 browser scenarios, external trust and exact state anchor checks, and full regression (45507828119, 45507828058). The new opt-in collector polls the operator-owned local inbox, not external sources. Run node research/unified-live/collector.mjs <inbox> <state-dir> <trust-file> <plan-file> <trusted-plan-sha256> [interval-ms max-cycles]. The independently approved plan is JSON with kind APPROVED_COLLECTION_PLAN, schemaVersion 1, trustSha256 and approvedDigests (1–100 distinct SHA-256 fingerprints of explicitly approved batch files). Trust and plan files must be outside inbox and state, and the plan fingerprint must come from a separately trusted record. The collector never derives new approvals from incoming reports. Every cycle rechecks the unchanged plan and trust registry, and only submits an allowlisted batch through signedSynchronise. An in-process processed set avoids repeating accepted batches; the state engine retains its replay checks across restart. Already processed is not a new integrity or freshness check on inbox contents. Rejected attempts may be retried within the configured cycle limit; only redacted outcome receipts are emitted to standard output, not a durable incident ledger. The default is 20 cycles every 15 seconds. Intervals 1–60 seconds, at most 240 cycles and at most one hour of configured interval budget; this is not a hard wall-clock bound on synchronous filesystem operations. Ctrl+C or SIGTERM requests stop between cycles. Changed or unavailable trusted configuration stops the collector. New approvals require a newly reviewed plan and restart. No daemon, automatic key provisioning, new revision promotion, network fetching or producer execution. CI uses ephemeral test keys and historical inputs only. New tests pending.

The external manifest is JSON with kind SOURCE_REVISION_REVIEW, schemaVersion 1, baselinePinsSha256 (exact bytes of the inherited source-pins.json), and six ordered sources with id, head, reportRevision, run, artifact and summarySha256. The tool checks all six report hashes and reuses existing source-specific summary contracts; a changed schema or reference date may require adapter development. It emits a deterministic review receipt, never changes active pins, approval files or state, and never authorizes promotion. ## Isolated revision activation

Baseline 2eaa6cc passed 41 tests, 13 browser scenarios, six actual baseline source contract reviews, Phase 1 regression and full regression (45508996180, 45508996100, 45508996229). The new activation tool creates a separate candidate runtime and state; it never switches the active viewer or collector. The operator must independently review candidate GitHub workflow/artifact provenance and retain trusted fingerprints before invoking it. The activation plan is JSON with kind APPROVED_ISOLATED_REVISION_ACTIVATION, schemaVersion 1, manifestSha256, reviewSha256, baselineStateSha256, trustSha256 and approvalSha256. All five values are SHA-256 fingerprints from reviewed records. The baseline must be a signed state matching both independently supplied anchors. The candidate must pass revision compatibility review with at least one changed revision and provide a new sequence-one signed approval covering exactly the reviewed six summaries under the same trust registry. Run node research/unified-live/revision-activate.mjs <candidate-dir> <active-state-dir> <trust-file> <review-manifest> <activation-plan> <trusted-plan-sha256> <new-runtime-directory>. The target must not exist; it must be separate from the source tree, candidate and active state. Only fixed trusted runtime modules are copied; candidate code is never executed. Candidate summary copies are staged temporarily, signed acceptance uses the existing engine, and source pins are changed only inside the separate runtime. The new state is anchored and checked against the review. A successful activation-receipt.json binds the old state, reviewed plan, new state and runtime file fingerprints. The operator must retain the receipt and fingerprints separately, and verify the runtime inventory before use. A failure cleans up the newly created target; interruption may leave an incomplete target, which must not be used without a completed independently retained receipt. No target overwrite or active state replacement is allowed. New namespace starts at sequence one; this is not a continuation of the old approval chain. There is no automatic migration, active viewer switch, production approval, independent candidate provenance verification or live producer configuration. To inspect the isolated candidate, run its runtime/unified-live/viewer.mjs with the new state directory, an unused loopback port, and the trust and candidate state anchors. New changed-revision acceptance tests use synthetic candidate metadata and ephemeral test keys only. Production remains UNVALIDATED and publication BLOCKED. New CI pending.
