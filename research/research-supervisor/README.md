# Research Supervisor — Phase 1

Separate stacked draft from green scientific compute commit 7c95c0bce1c428c0d9d24fd230f009304c289837. Reuses the existing registry supervisor and lifecycle reader; does not change them. Only inspect a dedicated, stable local registry. `node research/research-supervisor/supervisor.mjs <registry-directory>` returns aggregate lifecycle counts, stable incident identifiers, severity, recommended manual action and a store fingerprint. The adapter checks bounded, nonsymlink files, orphan lifecycle folders, checkpoint and terminal artifact bytes, event time ordering, long-running age and active synthetic-store locks. Unavailable counts remain null. Age is a review signal, not proof of a stalled job; fingerprints do not certify results. No automatic repair, resumption, source modification, model execution, protected data or production deployment. The CI workflow creates a disposable five-fixture synthetic registry using the existing laboratory and inspects it. Before/after checks are not atomic or hostile-filesystem isolation. Future stages: cross-report contract checks, incident history and static reporting, acceptance audit. No always-on service configured.

## Phase 2 — cross-report monitoring

`node research/research-supervisor/report-monitor.mjs <artifact-directory> <revision>` inspects fixed laboratory and scientific compute status summaries. It distinguishes missing evidence, inconsistent contracts and recorded failure from recorded synthetic passes; CPU and GPU are separate. Existing producer checks remain authoritative for underlying artifacts. CI generates actual disposable synthetic reports using the existing adapters and verifies the expected CPU pass / GPU missing combination. No GPU execution, protected data, automatic repair or live monitoring service. A missing GPU report is a review incident, not evidence of hardware failure. The CLI returns nonzero on a blocking inconsistency; review status remains visible in the report.

## Phase 3 — incident observation history

Create a separate empty local directory, then run `node research/research-supervisor/incident-history.mjs <history-directory> <registry-directory> <artifact-directory> <revision>`. Each invocation inspects existing sources without restarting workloads and appends a bounded, hash-linked observation using exclusive file creation. The same directory is scoped to a single declared revision. New, repeated, recurring, not-observed and unknown-coverage states are tracked; none implies verified closure. Incomplete coverage cannot resolve incidents. Existing evidence directories are never modified. An existing lock is not automatically removed. History is limited to 1000 observations; no automatic deletion. The hashes are not signatures, and the store is not an adversarial audit log or a continuous service. CI generates a disposable observation summary; the actual history is retained locally only.

## Phase 4 — recovery planning

`node research/research-supervisor/recovery-plan.mjs <registry-directory> <artifact-directory> <revision>` derives read-only recommendations from fresh registry and report inspections. Blocking incidents precede review items; every item states its category, recommended manual action, evidence requirement and approval requirement. Plans bind the exact observation reports with fingerprints and stable incident identities. Missing GPU evidence requests evidence acquisition, not device repair. No command execution, closure, automatic recovery or file modification occurs. Unknown incident types require manual review. A blocking plan returns a nonzero exit status while retaining its diagnostic output. Plan hashes are not signatures or permission; reinspection is required before action. CI tests the actual synthetic report combination and checks that no automatic action is present.

## Phase 5 — bounded local monitoring

Run `node research/research-supervisor/monitor-loop.mjs <history-directory> <registry-directory> <artifact-directory> <revision> <interval-seconds> <max-cycles>` explicitly in a foreground terminal. The loop performs sequential read-only evidence inspections and appends observations to the separate history directory. New and recurring incidents emit local JSON notices; repeated incidents are counted but suppressed. Blocking incidents stop the CLI by default. Ctrl+C or SIGTERM requests a stop between scans; a history conflict stops without removing the existing lock. Interval 1–3600 seconds, 1–120 cycles and at most one hour of scheduled waiting. The time budget is checked between scans, not a hard per-read deadline. No installed daemon, notifications to external services, automatic repair or experiment execution. CI exercises two real scans using disposable synthetic artifacts. No monitoring is started on user hardware by this change.

## Phase 6 — supervisor dashboard

`node research/research-supervisor/dashboard.mjs <registry-directory> <artifact-directory> <revision> json|html` performs a fresh pair of inspections and derives the recovery plan from those same reports. The static dashboard presents the registry counts (unknown when unavailable), subsystem states, blocking/review counts, recommended manual actions and required evidence. It never starts monitoring, modifies source evidence or executes repairs. CI generates JSON and HTML from the actual disposable synthetic fixture bundle. The page is a standalone preview; browser acceptance, integration with a deployed control centre and final audit remain outstanding. JSON and HTML CLI runs are separate observations and may have different timestamps and fingerprints.
