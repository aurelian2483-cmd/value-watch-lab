# Shared cloud/PC job controller — storage prototype

Stacked on accepted PR #190 at e927c2a70c482b465bab68f71325bcf6765cdaed. No existing code changed. This is a single-controller local SQLite prototype, not a hosted shared service. It supports a fixed job allowlist, pinned revisions, idempotent enqueue, uniqueness of logical jobs, atomic CPU leases, restart persistence, hashed lease tokens, replay rejection, expiry quarantine and a read-only-in-content snapshot (snapshot advances trusted time and records expiry). GPU jobs stay blocked. Receipt hashes are unverified references; no job becomes scientifically accepted. Worker labels and time are trusted in-process inputs, not authentication or remote attestations. No execution, network endpoint, credentials, worker registration, retries, provider data, schedule or deployment. Production and publication remain blocked.

Run: python -B -m unittest discover -s research/shared-job-controller -p 'test_*.py' -v

Next gates: authenticated service boundary and trusted server clock, durable hosted storage/backup, revocable worker identity, bounded fixed-job execution adapters, trusted receipt artifact intake, cross-host acceptance and fault tests. No shared network filesystem SQLite deployment. No unreviewed commands or automatic GPU fallback. Quarantined work requires explicit future reconciliation; never retry automatically. Do not expose this prototype to the internet.

## Phase 2 — security hardening

Baseline PR #191 controller QA run 45529569059 and full regression run 45529569084 passed at 0e8ef055e11b0ece70e95ae5e6569ba2ebe5cfce. Added queue lifetime capacity of 300, receipt digest deduplication across jobs, expiry reconciliation on enqueue, safe clock range, and a genuinely read-only stored-state view. Eight additional test scenarios cover roles, pinned revision, status immutability, revocation, wrong stored revision, receipt replay, capacity, invalid configuration and expired idempotent enqueue.

The in-process service separates operator, hosted CPU worker and observer credentials, comparing SHA-256 digests of separately provisioned high-entropy tokens. Use synthetic credentials only in tests; no real credentials committed. Time comes from server-side clock, with rollback rejection and fixed 240-second lease. Direct database access is a trusted administrative boundary. One service instance is intended; this is not a network authentication protocol, TLS endpoint, independently attested worker or cross-process authorization system. The in-memory revocation switch is lost on restart and does not terminate an already running task. Persistent revocation and cancellation are still required. The stored-state observer deliberately does not reconcile expiration and labels freshness accordingly. Capacity exhaustion is fail-closed; no automatic cleanup. GPU remains blocked. No job execution or deployment enabled.

Phase 2 acceptance and regression pending at time of writing. Research UNVALIDATED; production execution and publication BLOCKED.

## Phase 3 — durable policy and revocation

Phase 2 accepted at dfe933776a0afc3a24b5f2a26f806a1d788d1fb8: controller QA run 45529821342 and full regression 45529821365 both succeeded. The service now binds its revision and credential configuration by a persistent policy fingerprint. Authorization, revision scope and mutation share the same SQLite transaction; status checks authorization in its read transaction. Revocation persists across restart and service instances and quarantines active leases atomically. Five additional tests cover restart, changed policy, shared observer revocation, concurrent claim/revoke and repeated revocation. Phase 3 supersedes the in-memory revocation limitation above.

Revocation cannot stop computation already running outside the controller; it invalidates result intake only. Trusted direct administrative access, database rollback protection, policy rotation, external attestation and network transport remain outside this prototype. No production or GPU execution.

## Phase 4 — loopback TLS and isolated recovery

Phase 3 accepted at 9b80a16ad8276ff7c26e0ba4dee2616d12354591: controller QA 45530053477 and full regression 45530053441 both succeeded. Added five TLS transport and three backup/restore tests. TLS binds exclusively to 127.0.0.1 at an ephemeral port, checks a supplied certificate trust root and IP identity, requires role credentials, bounds request/response size, accepts only claim/submit/status, and never exposes operator operations remotely. A CI-only acceptance harness uses the existing approved fixed dispatch code to run two actual CPU jobs (known-answer probe and 500 synthetic checks) through that transport; GPU withheld, receipt hashes pending independent review. No external connection or executable request payloads. OpenSSL generates disposable test certificates and credentials never leave the temporary directory. No production certificate or remote service is provisioned.

Recovery uses SQLite's backup API and independently retained byte digests for isolated restoration into new paths. It validates database integrity, foreign keys and basic schema, and verifies that worker revocation and history survive a restored copy. It cannot prevent rollback to a legitimately older backup; do not promote restored candidates to a live service without independently anchored chronology and review. Local trusted directory permissions are required; database encryption at rest and hostile filesystem protections are not provided. TLS pilot is not a production HTTP server and provides no internet exposure, cross-host worker identity, rate limiting or persistent certificate rotation. No scheduler, remote enrollment, production execution, external research or publication enabled. Phase 4 CI pending.
