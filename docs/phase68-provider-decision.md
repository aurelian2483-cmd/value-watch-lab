## Recommendation

**Approve a two-provider, private test pilot for football and horse racing first.** Evaluate football-data.org fixture/result IDs and The Racing API GB/IRE race/runner IDs with the existing credential conventions. Request only fixtures and completed results after access and retention decisions. For football prices, first confirm whether the documented football-data.org add-on exposes exact bookmaker identity and quote times for the chosen leagues. For racing, obtain a Pro entitlement decision only if timestamped price history is required. Neither pilot authorizes scoring or publication.

For later expansion, evaluate one shared market feed, The Odds API, for NFL and tennis first, then rugby, basketball, cricket and golf as rights and scope permit. Use its documented event IDs as a proposed market crosswalk, never as an independent outcome source merely because it has a different hostname. Use Sportradar only if an approved fixture/results package is needed across the expansion sports. Its products and packages need separate confirmation. Darts stays blocked pending exact coverage and an approved odds source. A minimal initial two-provider test cannot satisfy every sport's independent verification or settlement requirement.

## Integration sequence and decision gates

1. **Rights owner approves one written scope per pilot.** Record exact product/tier, named competitions, private/public display, raw bytes and redacted/hash retention, withdrawal/deletion policy, attribution, and prohibited redistribution. Record the price ceiling and custodian. No purchase was made.
2. **Credential custodian injects only approved variables.** Reuse `FOOTBALL_DATA_API_KEY` or `RACING_API_USERNAME` plus `RACING_API_PASSWORD`. For expansion, provision only the selected supplier's proposed variable. Existing workflow names are configuration declarations, with no proof of secret presence or contract. GitHub rejected the repository secret-name listing with HTTP 403, so hosted secret presence remains unknown. `HORSE_RACING_API_KEY` and `DARTS_API_KEY` belong to distinct existing lanes and do not grant access to the candidates above.
3. **Independent reviewer validates exact identity.** Require namespace, stable ID, competition, ordered participants, UTC start and revisions, exact market/settlement, source and receipt time. Confirm upstream acquisition and adjudicate conflicts. Keep quote time, retrieval time, revision time and fixture cutoff distinct. Date-only records cannot prove prospective availability.
4. **Engineering tests a narrow read-only adapter after approval.** Set bounded request timeouts and byte limits, use the entitled quotas and retry-after/cooldown, verify response hashes and zoned timestamps, reject duplicate/conflicting records, preserve provenance and expose stale/error states. Test synthetic responses separately from permitted source receipts. Store approved private receipts before considering any public status. Passing connectivity or readiness alone grants no forecast or outcome eligibility.
